## Installed parser surface (read from the installed TA, not assumed)

- `props.conf` `[cisco:ise]` renames to `cisco:ise:syslog`; `SHOULD_LINEMERGE
  = false`; **`DATETIME_CONFIG = CURRENT`** — the add-on does not parse the
  embedded ISE timestamp; `_time` is assigned at indexing time by design.
- `props.conf` `[cisco:ise:syslog]`: `KV_MODE = none`; search-time extraction
  chain: `cisco-ise-extract-raw-message` (→ `MESSAGE_CODE`, `x_status`,
  `raw_msg`), `cisco-ise-raw-message` KV extraction with `MV_ADD=true` (hyphen
  vendor attributes land as hyphen-named fields), calling/called-station MAC or
  IP regexes, then `EVAL-*` user/src_ip/src_mac (normalized) and
  vendor/product/vendor_product fields.
- `transforms.conf` enforces `MESSAGE_TEXT`/`MESSAGE_CLASS` enrichment via
  lookup `cisco_ise_message_catalog_500.csv` (installed) and indexes
  `cisco:ise:syslog` routing for `syslog` transport via
  `cisco-ise-sourcetype` — **not exercised here** (HEC test; NOT APPLICABLE).
- `eventtypes.conf` matches message-code lists (passed/failed authentication,
  alert, endpoint service, change, etc.).

## Actual TA field extraction vs eventtype coverage (distinction)

Actual field extraction: all seven events produced `MESSAGE_CODE`, `x_status`,
`user`, `src_ip` (six of seven carry an IP; none failed parsing), with source
fields resolving through distinct native attributes (AdminIPAddress,
Remote-Address, Calling-Station-ID, Framed-IP-Address, device IP) — evidence
the extraction chain reaches per-class native attributes, not just a collated
message id. Eventtype coverage is a separate, narrower match: four of the five
tested original classes and both generated events fall inside installed
eventtype lists; **class 3302 does not**, and was recorded as N/A rather than a
pass. The eventtype verdicts were computed from the installed list membership,
not asserted from CIM training data.

## DATETIME_CONFIG=CURRENT vs embedded timestamps (distinction)

The installed add-on's design overrides `_time` with the indexing time. All
seven events show `_time == _indextime`; the embedded 2026-03-11 vendor
timestamps are retained verbatim inside `_raw` but never become `_time`. This
is recorded as **by-design behavior of the installed parser**, because any
consumer that needs the vendor ISE timestamp must re-derive it from `_raw`
requirements — no PASS/FAIL is assigned to that policy here.

- This validates the seven tested records only. **It does not validate all

  profiling, guest/portal, endpoint-move, category-specific audits), and any
  other message code family (including the documentation-cited 5205 CoA) remain
  unvalidated at Level D.
- Catalog sourcetypes beyond `cisco:ise:syslog` are untouched: **no other Cisco
  sourcetype is validated by this run**. Cisco ASA/FTD (Splunkbase 1620/6.1.2),
  the remaining `cisco:*` lanes, and the placeholder TA bindings recorded in
  `catalog/sourcetypes.json` remain Level A/B or not_assessed.
- C1 profile gates stand unchanged: the six existing Cisco seed profiles remain
  `not_assessed` with no added `validations`, enforced by
  `tests/test_integration_profiles.py`; this batch adds an evidence reference
  only and performs **no catalog promotion** (no `integration_verified` state
  change of any kind).
- CIM datasets, tags and dashboards were not exercised; parser success does not
  establish consumer compatibility (Level E unknown).
