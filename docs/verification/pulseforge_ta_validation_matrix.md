**How to read the verdicts.** Field extraction is measured against the fields *the event itself carries* (EventCode, Computer, every `<Data Name=...>`). It shows the vendor TA correctly parses what the generator emits; it does **not** show the generator emits every field a real source would. Verdict names say what was shown: `TA_PARSES_EMITTED_FIELDS` = the TA extracted every field the generated event carries (a self-consistency check, not a vendor-schema completeness check). `LIMITED_SAMPLE` means fewer than 3 events (one EventID) were tested, which is too thin to call the sourcetype validated. Timestamps were tested with a 48 h shifted event time (declared fixture transform); tags are what the TA assigned, not a CIM data model result.

Notes per row:

* `XmlWinEventLog:Microsoft-Windows-NTLM/Operational`: timestamp NOT parsed from event body: the TA props define no timestamp rule for this channel (props dump in the evidence JSON)

### Findings from the run

* **Metadata convention works with the Windows TA.** Events sent as NetSpout dispatches them (variant A: sourcetype `XmlWinEventLog:<channel>`, source `network-topology-simulator`) extracted exactly like the forwarder-canonical form (variant B): mean extraction A=0.976, B=0.976; the source predicate `source="XmlWinEventLog:*"` matched 14/14 for A because the TA's index-time fixup rewrites source and sourcetype.
* **Timestamps.** NetSpout's dispatcher sets HEC `time` to the send time, so variant A shows 0/14 event-time parses by construction of that path (a property of how NetSpout sends, not a TA result). With a forwarder-style path (B) only the Sysmon channel parses the event time (4/14); the Windows TA defines no timestamp rule for the other channels, and the TA props dump shows no timestamp rule for them. One authentic-bytes control (pinned Sysmon events relabeled to a channel with no rule, 0/3 parsed) is consistent with that; it only supports the timestamp conclusion, and it says nothing about field extraction or tags.
* **Tags.** Every event received TA tags/eventtypes (14/14); examples: 4624/4625 `authentication`, Sysmon 1/7/10 `process`+`report`, Sysmon 22 `dns`+`resolution`.
* **Not validated:** CIM data models (needs Splunk_SA_CIM), detection outcomes (needs ESCU content/macros), ES notable behavior, TA behavior on a real Windows forwarder.

## 3. Test definitions (apply to every row)

| ID | Test | Pass criterion |
|---|---|---|
| T1 | Install verified | TA app visible with expected version and its props.conf stanzas visible through /configs/conf-props (not just files copied) |
| T2 | Metadata convention | Same raw sent (A) as NetSpout dispatches and (B) as a forwarder would; both must reach the TA's parsing |
| T3 | Timestamp | Event timestamp moved 48 h into the past; _time must equal it where the TA defines a timestamp rule; an authentic control shows what is TA behavior |
| T4 | Field extraction | Every field the event itself carries (EventCode, Computer, each Data Name) must appear as an extracted field (space/underscore-normalized) |
| T5 | TA tags/eventtypes | Tags the TA assigns are recorded (CIM-relevant: authentication, process, dns, ...) |
| T6 | CIM data model | Requires Splunk_SA_CIM installed; datamodel search must return the events. NOT RUN while CIM is absent |
| T7 | Detection outcome | A relevant detection's SPL (with its macros) must match naturally generated events. NOT RUN while ESCU macros are absent |
| T8 | Authentic control | Pinned authentic bytes through the same path to separate generator fidelity from TA behavior |

## 4. Missing inputs (exact)

* Authenticated Splunkbase downloads (user action; this repo never downloads TAs): packages listed in the backlog table. For ISE, re-fetch 1915 5.0.0 (sha256 `7c5c1489d11744cfe6270f4f28f109e46b94f65a77f1624bcbb13d0ceb629b80`) because the prior copy was on an unmounted volume.
* Splunk Common Information Model (`Splunk_SA_CIM`) for T6.
* Splunk ES Content Update (ESCU, `DA-ESS-ContentUpdate`) for T7: the repo does not contain ESCU macro definitions, and none were written here.
* Confirm Splunkbase IDs before download: `catalog/vendors.json` IDs disagree with `telemetry_catalog.json` and with the ISE-verified ID (for example ISE 2736 vs 1915; ASA 6259 vs 7404), and `required_ta` was wrong for 100 Cisco rows (it claimed the Unix and Linux add-on). Those rows now carry `required_ta: null` plus a `required_ta_review` record (previous value, vendor-level candidate NAME from vendors.json, status UNVERIFIED); no replacement ID is asserted. Update 2026-10-30: 37 of those rows now have `required_ta` set because the Splunkbase release metadata declares that exact sourcetype (status VERIFIED_DECLARED_BY_SPLUNKBASE, declaration only, parsing NOT validated); 63 remain UNVERIFIED. See `pulseforge_splunkbase_gap_analysis.md`. Rows for linux_infrastructure, splunk and sc4snmp were not shown to be wrong and are unchanged.
